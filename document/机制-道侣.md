# 机制 · 道侣（DAOLV）

> 信徒仓库卡片内的「💞 道侣」区块提供一条**消耗型**长期增益：把一位同修「化道」纳为道侣，
> 对方从仓库永久移除，纳者永久保留其加成。每名信徒最多 7 位道侣，**结契后不可解除**。
> 加成只放大该信徒自己的任务加成（速度 / 经验 / 掉落），不影响朝代职位与洞天产出。

## 1. 消耗规则

| 项 | 规则 |
| --- | --- |
| 纳者 A | 保留在仓库，道侣位 +1，永久获得加成 |
| 被纳者 B | **从 `owned` 永久移除**，不可恢复，也不能再出现在任务席位、朝代职位与道侣候选中 |
| B 的驻守任务 | 若正在驻守任务，结契时**自动卸下**（`assign` 不留悬空 uid） |
| B 的朝代职位 | 若正在任职，结契时**自动空缺**（`dynasties[].posts` 置 `null`） |
| B 的既有道侣 | B 原有的道侣关系全部**寡妇化**：对方那一段记录标记亡故、道侣位永久占用、加成归零 |
| 招募费 | B 被消耗**不退还**招募费；`disciples.peak` 不变（招募费仍按历史峰值只增不减） |
| 道侣位 | A 最多 `DAOLV.MAX = 7` 位；被消耗者的道侣位容量**不参与判定**（只检查 A） |
| 解除 | 无解除入口；亡故（`state='dead'`）记录同样永久占位、不释放 |
| 动作槽 | 结契 / 查看都不占用动作槽 |

候选人（`discDaoCandidates()`）= 仓库内除自己以外、尚未与自己结契的所有信徒。
对方即使已有 7 段道侣关系、或正在驻守任务 / 担任朝代职位，也可以被选中——
这些后果会在确认弹窗里逐项列出（v2.12.2 起走应用内确认弹窗，确认按钮为唯一执行入口）。

## 2. 加成公式

```
主属性强度 mainPower = round(power × MAIN_MULT[tier], 3)
单段加成  seg       = 0.5 × mainPower(other) + 同主 / 相生系数
信徒加成  bonus     = Σ seg（跳过 state = 'dead' 的记录）
任务实际加成 = 基础加成（主属性命中 / 副属性命中） × (1 + bonus)
```

- `DAOLV.RATE = 0.5`：单段基数取对方主属性强度的一半。
- `DAOLV.SAME_MAIN = 0.02`：双方主属性相同。
- `DAOLV.GENERATES = 0.01`：对方主属性**生我**（金→水→木→火→土→金）。
- 记录保留**化道瞬间的快照**（`tier` / `main` / `power`），B 消失后仍可照常计算；
  旧档 `alive` 记录改用仓库里的实时实例（`daoRecordSource()`）。
- 合计值作为乘数同时放大「速度 / 经验 / 掉落」三项任务加成（`elemBonus()`），
  不改朝代职位加成，也不改洞天产出。

## 3. 数值表

`ELEM_POWER` 为副属性基准，`MAIN_MULT` 为主属性倍率，副属性强度在基准 ±20% 内浮动：

| 品阶 | 副属性强度 | 主属性强度 | 单段基数（0.5×） | 同主单段 | 相生单段 |
| --- | --- | --- | --- | --- | --- |
| 凡品（1） | 2.0%（1.6~2.4%） | 4.0%（3.2~4.8%） | 2.0%（1.6~2.4%） | 4.0% | 3.0% |
| 灵品（2） | 3.0%（2.4~3.6%） | 6.6%（5.28~7.92%） | 3.3%（2.64~3.96%） | 5.3% | 4.3% |
| 仙品（3） | 4.5%（3.6~5.4%） | 10.35%（8.28~12.42%） | 5.175%（4.14~6.21%） | 7.175% | 6.175% |
| 神品（4） | 6.5%（5.2~7.8%） | 15.6%（12.48~18.72%） | 7.8%（6.24~9.36%） | 9.8% | 8.8% |

- 典型满编（7 段神品、同主属性、强度居中）：`7 × 9.8% = 68.6%` → 任务加成 **×1.686**。
- 理论上限（7 段神品同主且强度全部上浮 20%）：`7 × (9.36% + 2%) = 79.52%` → **×1.795**。
- 一段关系都没有时为 ×1.000；单段最多 2 位小数口径随 `Math.round(v × 10000) / 10000` 收敛。

## 4. 存档结构

道侣记录挂在**纳者**的信徒实例上（`state.disciples.owned[i].dao`）：

```js
dao: [ // 长度 ≤ DAOLV.MAX，顺序即占用顺序
  { uid, id, tier, main, power, state }
  // uid   对方 uid（唯一，表内不允许重复、不允许等于自己）
  // id    对方身份（目录 id，用于显示名称）
  // tier  品阶 1~4（化道快照）
  // main  主属性（metal / wood / water / fire / earth）
  // power 副属性强度快照（夹在该品阶 ±20% 区间内）
  // state 'spent' 已化道（加成生效） / 'dead' 亡故（无加成） / 'alive' 旧档对称绑定
]
```

- 已化道者（`spent`）**不允许**继续留在 `owned`：读档时凡被声明 `spent` 的 uid 一律移出仓库。
- 兼容字段 `rec.alive`：`spent` 记录删除该字段，其余按 `state !== 'dead'` 重写（仅供旧界面读取）。

## 5. 旧档迁移与校验

v2.11.0 的关系是**对称**绑定（双方的 `dao[]` 各存一条、对方仍在仓库）；
v2.12.0 改为**化道式单向**绑定。`mergeState` 读档时按下表收敛：

| 情况 | 处理 |
| --- | --- |
| `dao` 非数组 | 视为空数组 |
| 记录非对象 / `uid` 非法或为空 / 自引用 / 表内重复 | 丢弃该条 |
| 对方实例与身份目录**都不存在** | 丢弃（无法显示也无法计算） |
| 旧档无 `state` | 对方仍在仓库 → `alive`；否则 → `dead` |
| `state = 'dead'` 或 `alive === false` | 归一化为 `dead` |
| `state = 'spent'` | 保留为 `spent`，并把该 `uid` 记入 `consumed`，读档末尾从 `owned` 移除 |
| `tier` 非法 | 优先用对方实例品阶；否则夹到 1~4；缺失取 1 |
| `main` 非法 | 优先用对方主属性；否则随机补一个合法五行 |
| `power` 非法 / ≤0 | 优先用对方强度；否则取该品阶区间中值 |
| `power` 越界 | 夹到 `[base×0.8, base×1.2]`（`base = ELEM_POWER[tier]`），保留三位小数 |
| 条数 > 7 | 截断到 7（多余记录所在的加成不生效、但也不报错） |
| `alive` 对称修复 | 只对非 `spent` 记录做两轮：缺反向记录则补一条；一侧 `dead` 则双向 `dead`；对方位已满则本侧标 `dead` |
| 被消耗者残留 | `consumed` 集合中的 uid 从 `owned` 移除后，其余记录中指向它们的非 `spent` 记录一律标 `dead` |

校验的最终目标是三条不变式：**`spent` 者不在仓库**、**`dao` 里没有悬空 uid**、
**`assign` / 朝代职位里没有已消失的信徒**。遣散、朝代合成、结契三条路径都通过
`daoWidow(uid)` 统一把指向该 uid 的记录标记为亡故（永久占位、加成失效、不可补位）。

## 6. 界面

- 信徒仓库卡片底部「💞 道侣」：`已用 / 7`，逐条 chip 区分「已化道（加成生效）/ 亡故（占位无加成）/ 旧档存活（实时加成）」。
- 未满 7 位时显示空位「＋」与下拉「选择同修结为道侣（对方将化道）」；已满时只留空位提示。
- 结契确认弹窗（应用内）逐项写明：对方将被永久移除、其在任务 / 职位上的后果、
  其既有道侣关系会全部断绝，以及本次可获得的加成基数与占用后的道侣位数。
- 遣散确认弹窗会额外统计「在世道侣 / 已化道 / 亡故」数量，提示删除后哪些对应位会永久空缺。
