# 机制 · 任务系统

> 相关代码：`js/data.js`（`TASKS`、`TASK_PROD_SKILLS`、`TASK_ELEM_SKILLS`）、`js/engine.js`（`condDone/taskDone/taskProgress/checkTasks/claimTask`）、`js/ui.js`（`renderTasks/updateTaskState`）、`js/main.js`（`claim` 事件）

任务是**成就式**的引导与奖励系统：达成条件后解锁「可领取」状态，玩家主动领取奖励。v2.13.0 起任务链由新手期扩展到满级（太上境九万六千五百层），形成连续的阶段目标。

---

## 1. 设计目标

- **全程有任务可做**：从第一次采集到太上境满级，每个成长阶段都有可达成的目标。
- **奖励不通胀灵石**：新增任务一律不发灵石，奖励改为生命之种、星砂、丹药、装备、信徒，避免任务成为灵石印钞机。
- **进度挂钩真实系统**：境界、技能、锁妖塔、穿越、朝代/职位、道侣、阵法、洞天建设度、精通、信徒、秘境、签到均接入判定。
- **兼容旧存档**：`state.tasks` 仍以任务 `id` 为键，旧任务 id 与条件全部保持不变，已领取状态原样保留。

| 炼虚问道 | 15 | 炼虚期与大圆满、五行五职 100、塔 100、穿越 5 次、3 座朝代、4 个职位、3 对道侣、建设度 60、技能 60、神品信徒、太上境 1 层 |
| 太上初境 | 8 | 太上 100 层、穿越 10 次、5 座朝代、8 职位齐备、阵纹 40、塔 200、建设度 100、技能 70 |
| 太上高階 | 14 | 太上 500 / 1000 / 2500 / 5000 / 10000 / 25000 / 50000 / 96500 层、穿越 20 次、塔 500、建设度 150、技能 90、夏朝、精通 40 |

设计理由：

- **前期密、后期疏**：前期每 10~20 分钟就有一条新任务，帮助建立循环；后期以境界千层、塔百层、建设度 50 级为节点，避免高频打卡。
- **境界主线贯穿始终**：太上境 96500 层不可能逐层设任务，采用 1 / 100 / 500 / 1000 / 2500 / 5000 / 10000 / 25000 / 50000 / 96500 的里程碑阶梯，与现有突破节奏一致。
- **系统交叉覆盖**：锁妖塔、穿越、朝代、职位、道侣、阵法、洞天、精通、信徒、秘境各设 1~3 条，保证每个系统都有任务牵引，但不会强迫玩家只玩某一套。

## 3. 任务结构

```js
{
  id, phase, name, desc,
  cond: { type, ... },
  reward: { gold?, spirit?, stardust?, seed?, items?: [{id, qty}], disciple?: { tier } }
}
```

- `phase`：仅用于任务面板分组展示，不参与判定、不写入存档。
- 进度记录：`state.tasks[id] = { done, claimed }`。
- **达成**（`done`）与**领取**（`claimed`）是两个独立状态。

## 4. 条件类型（`cond.type`）

| type | 判定 | 数据来源 |
| --- | --- | --- |
| `gathered` | 累计采集次数 ≥ n | `state.stats.gathered` |
| `kills` | 累计击杀 ≥ n | `state.stats.kills` |
| `crafts` | 累计炼制（配方）次数 ≥ n | `state.stats.crafts` |
| `pills` | 累计炼出丹药数 ≥ n | `state.stats.pills` |
| `breaks` | 累计突破成功次数 ≥ n | `state.stats.breaks` |
| `level` | 指定技能等级 ≥ lvl | `state.skills[skill].lvl` |
| `realm` | 境界阶数 ≥ stage | `state.skills.cultivation.lvl` |
| `item` | 累计获得某物品 ≥ qty | `state.stats.gained[id]` |
| `alllevel` | `skills` 列表内全部技能 ≥ lvl | `state.skills` |
| `tower` | 锁妖塔最高层 ≥ n | `state.tower.best` |
| `cross` | 穿越次数 ≥ n | `state.planet.cross` |
| `dynasty` | 朝代数量 ≥ n | `state.world.dynasties.length` |
| `era` | 最高朝代序号（1 起算）≥ n | `dynMaxEra()` |
| `post` | 所有朝代在任职位总数 ≥ n | `dynPostCount()` |
| `dao` | 活跃道侣对数 ≥ n | `daoPairs()`（`alive` 双向记录折半） |
| `form` | 所有阵纹等级合计 ≥ n | `formTotalLevel()` |
| `world` | 洞天建设度 ≥ n | `worldLevel()` |
| `mastery` | 任一精通等级 ≥ lvl | `maxMasteryLevel()` |
| `disciple` | 信徒仓库数量 ≥ n | `state.disciples.owned.length` |
| `dtier` | 指定品阶（tier）信徒数量 ≥ n | `discTierCount(tier)` |
| `dungeon` | 所有秘境累计通关 ≥ n | `totalDungeonClears()` |
| `checkin` | 累计签到天数 ≥ n | `state.checkin.total` |

> `stats.gained[id]` 在 `invAdd` 时单调累加，可统计「累计获得」而非「当前持有」。
> 条件判定统一收敛到 `condDone(cond)`，任务与市集解锁共用同一实现，避免两套口径。

## 5. 奖励类型与经济口径

| 字段 | 说明 | 使用阶段 |
| --- | --- | --- |
| `gold` | 灵石 | 仅保留在 v2.13.0 之前的 10 条旧任务中，新任务不再发放 |
| `spirit` | 灵力 | 旧任务保留；新任务不使用 |
| `stardust` | 星砂 | 新任务主奖励，按阶段 8 → 50000 |
| `seed` | 生命之种 | 新任务主奖励，按阶段 1 → 300 |
| `items` | 丹药 / 装备 / 材料 / 种子 | 偶数阶段补充，帮助跨过门槛 |
| `disciple` | 随机神品信徒 ×1 | 仅 3 条里程碑任务（信徒 3 位 / 8 职位 / 满级） |

数值理由：

- 星砂与生命之种是洞天、阵法、朝代、道侣的硬性消耗品，发奖励不会稀释灵石购买力。
- 星砂投放按「一个阶段内阵法总消耗的 1/10 ~ 1/5」设计：前期 8~50，元婴前后 120~400，炼虚 600~800，太上每档 1000~50000。不会让玩家一次性点满阵法，但能明显缩短卡点。
- 生命之种按「朝代召唤 + 合成」的消耗节奏投放：前期 1~4，中期 5~15，太上 20~300。满级奖励 300 对应后期多次合成需求。
- 丹药与装备只给当前阶段「刚好用得上」的一档，不提前发放越级神装。
- `disciple` 奖励领取前校验招贤殿容量：未建造或仓库已满时**拒绝领取并提示**，任务保持可领取，避免奖励丢失。

## 7. 流程

### 7.1 达成检测（`checkTasks`）

- 每秒（`taskTimer`）遍历 `TASKS`；
- 未达成的任务若 `taskDone` 为真 → 置 `done = true`，写一条「可前往任务面板领取奖励」的日志；
- 已达成的任务不重复提示。

### 7.2 领取（`claimTask`）

- 前置：任务存在、`done` 为真、未 `claimed`；
- 若奖励含 `disciple`：先校验招贤殿容量，不满足则拒绝领取并提示（任务保持可领取）；
- 置 `claimed = true`；
- 发放 `gold` / `spirit` / `stardust` / `seed` / `items` / `disciple`；
- `invAdd` 发放物品（背包满时可能失败，需先清理背包）。

## 8. UI 表现

- **侧栏「📜 任务」**：显示达成 / 总数进度。
- **任务面板**：按 `phase` 分组，每组标题显示「已领 X / N」；每条任务显示名称、描述、进度、奖励预览。
- 任务进度（`taskProgress`）通过 `data-taskprog="任务id"` 占位节点由 `updateTaskState()` 增量写入，**不进入 `setHTML` 的内容签名**，避免进度变化触发整树重建。
- 状态：
  - 未达成（置灰，🔲）；
  - 已达成待领取（高亮 🎁 + 「领取」按钮）；
  - 已领取（✅，降低透明度）。
- 领取按钮绑定 `data-act="claim"`。

---

## 9. 存档兼容

- `state.tasks` 仍以 `id` 为键，v2.13.0 之前完成的 10 条任务 id、条件、奖励完全未变，`mergeState` 原样保留 `done/claimed`。
- 新增任务在 `mergeState` 中不会凭空写入；由 `checkTasks` 首次遍历时按需创建默认记录。
- 新增 `phase` 字段只存在于配置层，不写入存档。

## 10. 扩展指引

新增任务：在 `TASKS` 追加条目即可，`phase` 决定分组，`cond` 选取已有类型（或扩展 `condDone` 增加新判定）。若新增条件依赖新的存档字段，需同时在 `state.js` 的 `defaultState` 与 `mergeState` 中补默认值与兜底。
